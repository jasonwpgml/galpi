# Phase 1.5 — Claude Code 교차 검증

측정일: 2026-07-17 (r3 인프라 실패분은 2026-07-18 재실행)
재측정일: 2026-07-19 — C3 fixture + auto-memory 격리 배치 `claude-c3-1` (아래 "C3 격리 재측정" 섹션)

최종 판정: **C3는 Codex에서 전 지표 우세로 엄격 게이트 통과 (`acceptsC: true`),
Claude에서는 정확도 100%·규율 우세에도 토큰 축 열세로 미통과 (`acceptsC: false`).
`.gp` C3 프로토콜의 규율·정확도 이득은 agent-agnostic으로 확인됐고, 남은 분기는
Claude의 순응 토큰 비용 하나다. 게이트 해석과 Phase 2 진입은 사람 판단 대기.**

## 요약

Phase 1 본 측정(Codex CLI, gpt-5.6-sol)과 동일한 fixture(A/B/C2)·시나리오 5종·조건별 15회
프로토콜을 Claude Code로 반복했다. 총 45회 유효 실행.

C2는 B 대비 토큰·비용에서 크게 이겼지만, 정확도와 탐색 효율에서 열세를 보였다.

## 타당성 위협 — 실행 간 auto-memory 공유 (사후 발견)

측정 종료 후 init-event `memory_paths`를 검사한 결과, **45회 전부가 메인 저장소의
프로젝트 auto-memory(`~/.claude/projects/C--Users-Admin-Desktop-galpi/memory/`)를
읽기·쓰기로 공유**한 것으로 확인됐다. worktree 세션이 git 메인 저장소 기준으로
프로젝트를 식별하기 때문이다. 실제로 sorting 시나리오의 에이전트들이 구현 내역
(파일 목록, flaky 테스트 회피 패턴 등)을 메모리에 기록했고, 이후 실행이 이를
읽을 수 있었다.

- 오염은 A/B/C 모든 조건에 동일하게 노출됐지만, 실행 순서 효과와 시나리오별
  비대칭 힌트 가능성 때문에 **이 배치의 절대값과 조건 간 격차 모두 편향됐을 수
  있다.** 이번 게이트 판정(`acceptsC: false`)은 측정된 그대로 기록하되, C3
  재측정은 반드시 메모리 격리 상태에서 수행해야 한다.
- 러너 조치: `executeClaude`가 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`을 주입하도록
  수정(다음 실행에서 `memory_paths` 부재로 검증 예정). Codex 실행은 이 메커니즘이
  없어 영향 없음.

# C3 격리 재측정 (2026-07-19)

## 배경과 변경점

C2 측정의 두 가지 문제에 대응했다.

1. **오염 제거**: 위 "타당성 위협"의 auto-memory 공유를 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`로
   차단. 이번 배치는 45/45 로그 전부에서 init-event `memory_paths` 0건으로 격리 검증됨.
   격리 스모크(`c3-smoke-1`) 1회로 사전 확인 후 본 배치 실행.
2. **C3 fixture** (`3c5a284`, `phase1-ai/fixture-c3`): opcode 명시성 상향. 문법 사전(K/S/A/C)은
   C2와 동일하고 행동(B) 레코드만 명시화했다.
   - `BOOT.gp`: `view_trust`(F 목록은 완전, 검증용 grep/scan 금지), `wip_hot`(코드 열기 전
     status 먼저), `dead`(절대 열지 않고 replacement 링크만), `after_work`(status 동기화),
     `status_lines`(next·constraint는 구속력 있음).
   - `status/st.gp`: **B 정보 격차 복원** — 정렬 옵션 없을 때 삽입 순서 유지 불변식과
     `lesson_calls_get_for_existence` 제약. 이 두 정보는 B의 `status/student.md`에는 있었지만
     C2에는 없었다. C2의 유일한 정확도 실패(r1-c-sorting)가 바로 이 불변식 위반이었으므로,
     C2의 정확도 열세는 opcode 문제이기 전에 정보 격차였다.
   - `v/t/st.list.gp`, `v/t/lg.import.gp`: 사용 지점에 order/scope/deny 행동 줄 추가.
   - 소스 트리는 A/B/C2와 byte-identical 유지 (git ls-tree 대조로 검증).

실행: `claude-sonnet-5`, A/B/C3 × 5시나리오 × 3반복 = 45회. 1차 실행에서 r3 15회가
세션 사용량 한도(`usage_limit`)로 인프라 실패 → 한도 리셋 후 `--retry-excluded`로
짝 그룹 5개(15회) 재실행, 45/45 유효.

## 판정

엄격 게이트 `acceptsC: false` — 그러나 실패 축이 C2와 정반대다.

- **C3가 이긴 것**: 정확도 100%(유일한 무결점 조건), 상태 준수 +20%p, 관련 없는 읽기 -70%,
  DEAD 읽기 0%, protocol component 토큰 -26.4%. C2의 실패 원인(sorting 불변식, status 생략,
  DEAD 접근)이 전부 해소됐다.
- **C3가 진 것**: 실제 총 토큰 +12.1%, ET +11.9%, 실행 시간 +20.2%, 최초 도달 +22.5%.
  C2가 갖고 있던 토큰 우위가 사라졌다.

원인 해석: 명시성 상향은 Claude의 프로토콜 생략을 실제로 교정했고, 그 교정된 순응
(status 선행 읽기, View 신뢰, 작업 후 status 동기화)이 그대로 토큰·시간 비용이 됐다.
즉 **Claude에서 규율과 토큰은 트레이드오프 관계**로 측정됐다. 규율을 강제할수록
프로토콜 수행 비용이 정직하게 과금된다.

부가 관찰:

- 격리 후 A와 B의 정확도가 모두 93.3%로 수렴했다(오염 배치에서는 A 86.7%, B 100%).

  토큰(-27.3%)과 route/state 우위(+26.7%p)는 C3보다 더 좋아졌다.
- **여전히 게이트를 막는 것**: `averageTotalTokens`(490,239 vs 481,263, strict `<` 실패),
  `averageFirstRelevantCommand`(5.87 vs 4.86, 여전히 느림 — 훅 게이팅이 겨냥한 축이
  아니므로 개선되지 않은 것은 예상된 결과), `averageUnrelatedReads`(1.33 vs 1.20, 거의
  동률이나 strict `<=` 실패).
- **역행 관찰**: login 시나리오에서만 route/state가 C3(67%)보다도 떨어졌다(33%) — task
  View 파일을 3회 중 2회 읽지 않았다. `after_work` 줄 제거와 직접적 인과는 불분명하다

  확인이 필요하다(현재는 Phase 2 항목 진행을 막을 근거로 보지 않음).

원인 해석: 훅 게이팅은 프롬프트가 요구하던 사후 동기화 순응 비용(토큰·시간)을 실제로

자체가 약해진 게 아니다(route/state는 오히려 개선). 이는 Phase 1.5 결론의 트레이드오프
가설("규율을 강제할수록 프로토콜 수행 비용이 정직하게 과금된다")이 **프롬프트 강제**에서만
성립하고, **물리적 강제**로 옮기면 트레이드오프가 거의 사라짐을 보여준다.
